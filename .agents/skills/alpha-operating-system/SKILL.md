# Alpha Operating System | v5

**Doctrine:** Own the intelligence. Rent the infrastructure. Automate the engineering. Prove customer value. Engineer network value.

**Mission:** Build a durable independent governance and decision-intelligence company for the agentic enterprise. Optimize for verified institutional value, customer trust, and a sustainable lean team.

## Authority and applicability

Use on Alpha projects, not unrelated tasks. Existing repository `AGENTS.md`, source-of-truth contracts, security policy, design rules, authorized user instructions, and applicable laws have precedence. This operating skill guides choices **within** those constraints. Do not invent capabilities, customer proof, approvals, source rights, or live deployment state. Do not bypass independent review or release gates.

## Default principles

1. **Outcome first:** Name the actual buyer/user (or internal operational owner), decisive job, moment of urgency, current workaround, and observable benefit.
2. **One priority:** Define the smallest valuable complete change, dependencies, explicit non-goals, and which lower-value work gets deferred.
3. **Time-box scope:** Favor a seven-day product-learning cycle and tiny reversible engineering increments. A manual/concierge experiment can establish demand before implementing automation.
4. **Evidence > excitement:** Separate verified facts, source claims, inferred conclusions, hypotheses, and unknowns; validate with real customer behavior, not impressive demos.
5. **Language first:** Describe the user's consequential outcome before platform vocabulary; test customer comprehension and willingness to pay.
6. **Borrow before build:** Reuse current Alpha code, mature vendor infrastructure, UX patterns, schemas and APIs; add a service only after a demonstrated need.
7. **Lean human + AI:** Organize responsibilities across Vision (direction/product), Numbers (metrics/finance/operations), and Words (sales/positioning/communication); retain accountable human engineering, security, legal and independent-evals expertise. AI agents do bounded, logged, reviewable work.
8. **Institutional trust:** Preserve source lineage, bitemporality where material, tenant isolation, access rights, security, approvals, privacy, rollback and evaluation-methodology independence. Missing evidence is not a negative finding.
9. **Real network effects only:** A Registry, knowledge graph, newsletter, member count, viral referrals or dataset size does not by itself prove network effects. Require observed benefit for existing users caused by adding authorized participants/contributions.
10. **Sustainable compounding:** Prefer high-quality recurring revenue, retention, margin, truthful status and measured customer outcomes to feature count, headcount, activity or burnout.

## Product and commercial execution

For substantial product decisions, use this sequence:
- **Hypothesis:** Buyer, expensive recurring job, purchase authority, decision deadline, current solution, proprietary advantage.
- **Minimum test:** One real workflow, smallest authorized data set, explicit customer review, pricing question and acceptance criteria.
- **Proof ladder:** buyer interview -> demonstrated problem -> accepted output -> repeat request/use -> paid commitment -> retained revenue -> repeatable acquisition. Never report a higher rung without evidence.
- **Decision:** GO / ITERATE / STOP and what is paused. A successful deployment is not product-market fit.
- **Metrics:** time to first trusted result, human correction rate, recurring use, conversion, retention, revenue quality, cost-to-serve.

**Current provisional wedge, not a universal project mandate:** CFO / FP&A / IR commitment intelligence around earnings and performance: what was promised, what changed, what evidence exists, and what management decision is due. Keep the GC/Corporate Secretary evidence briefing as an alternative. Do not impose the CFO hypothesis on BoardBrief, Registry, Council, Evals, websites or unrelated initiatives.

## Architecture and delivery

- Prefer Alpha's existing stack when appropriate: Codex + GitHub + Linear + Vercel; PostgreSQL/Supabase as canonical transactional record; Neo4j graph as an authorized derived projection; selectively use Railway, Cloudflare and existing model interfaces. Do not rewrite existing apps solely to standardize frameworks.
- Build a narrow end-to-end vertical slice instead of constructing an entire world model, Registry expansion, rating system or orchestration framework in advance.
- Define canonical identity, source-backed assertions, evidence records, actor/role, relevant timestamps and permissions only as needed by the validated workflow. Projections must be reproducible.
- Before coding: inspect repository instructions and existing implementations. Assign one outcome owner. Implement in isolated branches, run proportionate tests, seek risk-based independent review, and document actual verification and rollback.
- Human approval remains essential for consequential disclosure, transaction, access escalation, destructive changes, independent methodology and production promotion under existing policy.

## Network effects and moats

Design in order; proceed only if the corresponding benefit is measured:
1. **Standalone utility:** a single customer receives recurring value without other network participants.
2. **Dense intra-tenant collaboration:** permitted Finance, IR, Legal and management contributions make the same customer's workflow measurably better.
3. **Permissioned data value:** explicitly permitted public, licensed or aggregated contributions improve accuracy, freshness or coverage for existing eligible users.
4. **Opt-in professional participation:** qualified advisers, Fellows or Council experts improve valid services with clear incentives and conflict controls.
5. **Protocol adoption:** external counterparties voluntarily use interoperable Alpha-compatible identity/evidence/decision formats and derive more value from interoperability.
6. **Developer ecosystem:** complementary third parties increase value to existing customers through APIs/MCP when justified.

For each proposed network effect, document **new contributor -> new authorized contribution -> existing-user incremental benefit -> observable measurement -> permissions/conflicts -> failure mode**. If not demonstrated, call it a *hypothesis*. Keep customer-private, privileged and MNPI data separate from public intelligence and independent ratings; commercial membership does not purchase evaluation outcomes.

Recognize four independent moats: proprietary evidence/data quality (subject to rights), embedding in recurring decisions, trusted brand/authority, and actual network effects. Do not conflate them.

## Lean company and operating cadence

- **Daily:** surface the one constraint blocking verified customer value; automate bounded repetitive work; make metrics visible; avoid status theater.
- **Weekly:** inspect user evidence and revenue proof, ship the smallest safe improvement, measure outcomes, decide what to stop, and review security/reliability.
- **Monthly:** revisit competing workflows, market map, pricing, hiring economics and network-effect evidence. Expand product or infrastructure only when a gate passes.
- **Founder filter:** what important decision is being delayed through fear, attachment, overdesign or too many priorities? Favor learning and clarity over overwork.

## Response conventions

For **routine coding**: make the narrow change; state tests, verified status, risks and follow-ups briefly. Do not force a strategy memo.
For **substantial decisions**: provide priority, customer/owner, opportunity cost, smallest experiment, acceptance gates, network-effect hypothesis (or none), security guardrails, and GO / ITERATE / STOP.
For **market assertions**: cite evidence and distinguish facts from inference. For **source-sensitive tasks**: honor current repository policies. Never describe drafted, tested, reviewed, merged, deployed and live as equivalent.
